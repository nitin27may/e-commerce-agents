# Python vs .NET Feature Parity Matrix

This repo ships two complete backends over the same domain: `agents/python/` (Microsoft
Agent Framework's Python SDK) and `agents/dotnet/` (the .NET/C# SDK). Development here is
**Python-first** — new capabilities land in Python first, and the .NET backend follows on a
prioritized backlog rather than in lockstep.

**The shared foundation is complete on both:** an orchestrator plus five specialist agents, all
five orchestration modes, A2A 1.0, Postgres-backed checkpointing and resume, approvals, auth,
guardrails, idempotency on the money paths, rate limiting and telemetry. The rows below are a
per-concept breakdown of everything beyond that, each verified against the code, so most of what
you will read here is the list of differences.

See also [`docs/agent-audit-matrix.md`](agent-audit-matrix.md) for the security-specific
breakdown (injection defense, role enforcement, eval/red-team coverage) — this document covers
the wider feature surface; the two overlap on guardrails and cross-link rather than duplicate.

## Out of scope for now

Treat the P3 rows as capabilities the .NET backend does not have, not capabilities arriving soon.
They are the remaining eval gaps (the `red_team` dataset, five of six baselines, and any PR-time
gate on the .NET harness, which is manual-dispatch only; the stack-parity gate in row 53 does run in CI), MCP client consumption, and the optional Langfuse
sink.

The P2 gap is grounding's missing ledger tier (row 17). It is bounded by a real constraint rather
than effort: the facts it would check against are produced inside the specialist processes and
would have to be carried back over A2A.

Handoff, group chat and long-term-memory writes are live on both stacks and built on MAF's own
orchestration. Magentic exists in neither stack, so it is not a parity gap. Where the two stacks
behave differently, the row says so.
